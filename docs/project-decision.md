# Журнал проектных решений (ADR)

Обоснования и согласования ключевых решений, принятых по ходу реализации.
Документ объясняет **почему** система сделана так, а не иначе.

**Статусы:** `принято` — действует; `временно` — компромисс до реализации;
`закрыто` — осознанный отказ или пересмотр.

## Архитектурные решения

### ADR-01. SQLAlchemy 2.0 Async

Ожидание ответа LLM занимает секунды; синхронный ORM блокировал бы event loop.
Async SQLAlchemy позволяет обслуживать другие запросы, пока агент ждёт модель.
Альтернативы: sync ORM (блокировки), raw SQL (сложнее поддерживать).

### ADR-02. Zustand

Минимальный бандл и простая интеграция с `persist` для токена и `store_id`.
Redux Toolkit избыточен, Context API даёт лишние ре-рендеры.

### ADR-03. Аргументы tools через Pydantic

Pydantic-модели дают валидацию аргументов и готовую JSON Schema для
OpenAI-совместимого API. Ручная JSON Schema ошибочна, LangChain — лишняя
зависимость.

### ADR-04. Изоляция через middleware

`TenantMiddleware` — единая точка проверки JWT и `X-Store-ID`. Фильтрация в
каждом сервисе повышает риск человеческой ошибки и утечки данных.

### D-15. Модульный монолит

Для 2–3 магазинов и команды из трёх человек микросервисы дают преждевременную
сложность. Слои `api/services/models/schemas` позволяют позже выделить модули.

## Продуктовые и объёмные решения

### D-01. Telegram-бот → бэклог

Бот дублирует уведомления PWA и не влияет на ценность ядра — рекомендации по
ценам. Ресурс итерации вложен в AI-агента и данные. Вернуться можно после MVP.

### D-02. PWA вместо нативного приложения

Единая кодовая база для Android, iOS и ПК, установка на главный экран,
офлайн-статика, камера из браузера без публикации в сторах. Экономия ~2–3 недель.
Риск: на iOS ограничены камера и фоновые уведомления.

### D-03. Write-CRUD справочников не делаем

Нормативный API ТЗ описывает только чтение справочников; наполнение — через
`seed_db.py`. Запись идёт через WMS и принятие рекомендации. Если понадобится
ручное управление каталогом — пересмотреть D-03 и вернуть задачу в бэклог.

### D-08. Семантика `accept` для `reorder` и `write_off`

В итерации 2 принятие таких рекомендаций меняет только статус на `accepted`,
без автоматического создания складской операции. Это упрощает контракт и не
смешивает рекомендацию с фактическим движением товара.

### D-09. Отдельный reject-эндпоинт

ТЗ требует отклонение рекомендации в UI, но в списке API описывает только
`accept`. Решение: добавить `POST /recommendations/{id}/reject`, который
переводит статус в `rejected` без изменения цены.

### D-10. Эндпоинт алёртов

`services/wms.py::alerts()` уже считает истекающие партии и остатки ниже
`min_stock`, но не отдаётся в API. Решение: `GET /inventory/alerts` с изоляцией
по `X-Store-ID`; используется дашбордом. Текущий дефект — BUG-03.

## Технические решения

### D-04. Внешний OpenAI-совместимый LLM API

На VPS нет GPU, поэтому используется внешний API. OpenAI-совместимый протокол
позволяет менять провайдера и модель через `LLM_API_URL` / `LLM_MODEL`.
Альтернатива — локальная модель, но она требует GPU и усложняет деплой.

### D-05. html5-qrcode

Сканирование камерой браузера без нативных сборок и разрешений магазинов
приложений. Альтернатива — нативный сканер, но он привязал бы проект к
мобильному приложению, от которого отказались в D-02.

### D-06. Расчёты только в Python

LLM не выполняет арифметику: цены, маржа, reorder и `expected_impact`
считаются в `services/calculations.py`. Это даёт корректность, покрытие
unit-тестами и прозрачность: в рекомендацию попадает готовое число из кода.

### D-07. JWT в `sessionStorage` (временно)

Токен переживает перезагрузку вкладки, но очищается при закрытии; это
осознанный UX-компромисс. Целевая схема — access-токен в памяти + refresh-token
в HttpOnly-cookie, тихий refresh и обработка 401. Реализация — BUG-06.

### D-11. Single-origin без CORS

В dev Vite проксирует API-префиксы, в Docker — nginx. Один origin упрощает
безопасность и убирает CORS. Следствие: пример `VITE_API_URL` в `web/.env.example`
некорректен — BUG-02.

### D-12. PostgreSQL 16

ТЗ требует PostgreSQL 15+; в compose и CI используется 16. Версия выше
минимальной, поведение совместимо, образ доступен как `postgres:16-alpine`.

### D-13. Детерминированный seed

Seed использует фиксированные генераторы и пересоздаёт данные при повторном
запуске: демо и тесты воспроизводимы, id стабильны. Рекомендации намеренно не
создаются — их должен генерировать агент.

### D-14. Рекомендации — серверное состояние

Список рекомендаций не persist в Zustand/localStorage: после accept/reject
делается refetch. Это исключает устаревшие статусы и расхождение с БД.

### D-16. Язык документации и коммитов

Документация и UI — на русском, сообщения коммитов — на английском в формате
Conventional Commits (`feat:`, `fix:`, `docs:` ...). Так удобнее команде и CI.

## Как пересматривать решения

1. Решение можно пересмотреть только явно: обновить статус и обоснование здесь.
2. Следом обновить `docs/requirements.md` / `docs/SDD.md`,
   если меняются требования или контракты.
3. Задачи на реализацию — в `docs/TODO.md`, дефекты — в `docs/BUGS.md`.
