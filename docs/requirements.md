# Нормативные требования (ТЗ)

> Сводка требований ТЗ к PriceMaster. Нормативна при расхождениях с проектной
> документацией. Детали реализации — `docs/SDD.md`, поведение LLM-агента —
> `docs/agents.md`, отступления и обоснования — `docs/project-decision.md`.

---

## 1. Цель и границы

PriceMaster — система агентного динамического ценообразования и складского
учёта для малого ритейла (сеть 2–3 магазина):

1. Упрощённая WMS: партии, сроки годности, приёмка, списание, минимальные остатки.
2. LLM-агент: анализ остатков, продаж и внешних факторов, рекомендации по ценам
   и закупкам.
3. Единое адаптивное веб-приложение (PWA) для мобильных устройств и ПК.
4. Сканирование штрихкодов камерой браузера.

---

## 2. Функциональные требования

### 2.1. Складской учёт (WMS)

- Приёмка: партия с `batch_date` и `expiry_date`, обновление остатков.
- Списание: фиксация убытка (порча, истечение срока) с обязательной причиной.
- Учёт остатков с разбивкой по партиям; алёрты за N дней до истечения срока.
- Минимальные остатки: порог `min_stock` на уровне `product_id + store_id`.
- Поиск товара по штрихкоду через API и камеру PWA.
- Списание партий — по FIFO: раньше истекает — раньше списывается.

### 2.2. Мультимагазинность

- 2–3 магазина в таблице `stores`; у каждого свои остатки и цены.
- Общий каталог `products`.
- Все транзакционные таблицы содержат `store_id`: `inventory`, `sales_history`,
  `price_history`, `price_recommendations`.
- Пользователь видит только данные выбранного магазина.

### 2.3. AI-модуль

- Роль агента — аналитик-консультант владельца магазина.
- LLM **не выполняет арифметику**: числа приходят из Python-инструментов.
- Системный промпт, триггеры вызова, JSON-валидация ответа и ограничения —
  `docs/agents.md` и `docs/SDD.md` §3.2.
- Обязательное поле рекомендации — `expected_impact` (методика — SDD §6.3).
- Триггеры: кнопка «Анализ» (`POST /recommendations/generate`) и события
  `quantity < min_stock`, `expiry_date < 3 дней`.

### 2.4. PWA

Экраны:

1. **Auth** — ввод Access Key.
2. **Store Selector** — выбор магазина.
3. **Dashboard Home** — KPI дня, топ-3 рекомендации, алёрты по срокам.
4. **Recommendations List** — список с кнопками «Принять»/«Отклонить».
5. **Product Card** — цена, остатки по партиям, история цен, график продаж.
6. **Scanner** — камера; после скана — карточка товара или форма приёмки.
7. **Stock Operations** — формы приёмки и списания.
8. **Analytics** — графики истории цен и продаж.

Требования: единый React + Vite, Mobile-first, PWA manifest (установка на
главный экран), адаптивность на iOS Safari и Android Chrome.

### 2.5. Аналитика

- `GET /analytics/sales`: история продаж для графиков с фильтрацией по магазину.

## 3. API

Приватные запросы требуют `Authorization: Bearer <JWT>`; запросы с данными
магазина — ещё и `X-Store-ID`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/login` | Выдача JWT по `access_key` |
| GET | `/stores` | Список доступных магазинов |
| GET | `/products` | Каталог товаров |
| GET | `/inventory` | Остатки с разбивкой по партиям |
| POST | `/wms/receiving` | Приёмка партии |
| POST | `/wms/write-off` | Списание по FIFO |
| GET | `/barcodes/{code}` | Поиск товара по штрихкоду |
| POST | `/recommendations/generate` | Запуск анализа агентом |
| GET | `/recommendations` | Список рекомендаций |
| POST | `/recommendations/{id}/accept` | Принять рекомендацию |
| GET | `/analytics/sales` | История продаж для графиков |

Дополнительные эндпоинты, добавленные решением команды (не входят в исходное
ТЗ): `POST /recommendations/{id}/reject` и `GET /inventory/alerts` — см.
`docs/project-decision.md` D-09, D-10.

---

## 4. Данные

9 таблиц: `stores`, `products`, `store_products`, `barcodes`, `inventory`,
`sales_history`, `price_history`, `external_factors`, `price_recommendations`.

Актуальные модели и ограничения — `backend/app/models/__init__.py`.
Ключевые требования:

- `store_id` во всех транзакционных таблицах;
- `price_history.recommendation_id` — nullable FK на рекомендацию;
- `inventory.quantity >= 0`;
- внешние ключи на `products`/`stores` — `ON DELETE RESTRICT`.

---

## 5. Безопасность

- `ACCESS_KEY` — первичный вход, используется только для выдачи JWT.
- JWT содержит `sub` и `store_ids`; хранится на клиенте согласно SDD §4.1.
- `X-Store-ID` сверяется со списком магазинов токена: чужой магазин → 403.
- Секреты (`JWT_SECRET_KEY`, `ACCESS_KEY`, `LLM_API_KEY`) не хранятся в коде.

## 6. Переменные окружения

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Подключение к PostgreSQL (`postgresql+asyncpg://...`) |
| `LLM_API_URL` | Адрес внешнего OpenAI-совместимого API |
| `LLM_API_KEY` | Ключ внешнего API |
| `LLM_MODEL` | Имя модели |
| `JWT_SECRET_KEY` | Секрет подписи JWT |
| `ACCESS_KEY` | Мастер-ключ первичного входа |

Полный пример — `.env.example`.

---

## 7. Критерии приёмки

**Итерация 1:** создание 2–3 магазинов; приёмка и списание через API;
консистентный seed-скрипт.

**Итерация 2:** рекомендация с JSON-валидацией и обоснованием; адаптивность
PWA; сканер ШК через камеру; принятие/отклонение рекомендации в интерфейсе.

**Итерация 3:** дашборд с таблицей рекомендаций и графиками; демо-стенд через
Docker Compose; работа с мобильного устройства и ПК.
